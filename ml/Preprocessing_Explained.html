1

Nettoyage du texte

Objectif : donner au modèle du texte propre, sans bruit. Chaque élément supprimé n'a aucun sens sémantique pour prédire le sentiment ou l'émotion — le garder forcerait le modèle à apprendre des patterns inutiles.
✂️ Suppression des URLs & adresses email Le modèle ne doit pas apprendre de domaines spécifiques
AVANT : "Check the PR at https://github.com/org/repo/pull/42 ASAP" APRÈS : "Check the PR at ASAP" AVANT : "Contacte support@client.com pour le contrat" APRÈS : "Contacte pour le contrat"

Pourquoi ? https://github.com/... ne contient aucune information de sentiment. Le modèle pourrait associer certains domaines à des classes, ce qui est un faux apprentissage.

✂️ Suppression des tokens base64 Spécifique aux emails Gmail avec pièces jointes
AVANT : "Attachment: data:image/png;base64,iVBORw0KGgoAAAANSUhEUgAA..." APRÈS : "Attachment:"

Ces blobs encodés apparaissent dans les emails Gmail avec des images ou fichiers joints. Ils font exploser la longueur du texte (plusieurs milliers de caractères) et dépassent immédiatement la limite de 512 tokens de XLM-RoBERTa.

✂️ Suppression des signatures & chaînes de réponse Bruit répétitif présent dans tous les emails
AVANT : "Le projet est bloqué depuis 3 jours. -- Sarah Hafsi | CEO | InsightFlow Tel: +216 XX XXX XXX > Le 12 juin 2026, à 09:14, Ahmed a écrit : > > Bonjour, peux-tu valider le budget ? > > Cordialement, Ahmed" APRÈS : "Le projet est bloqué depuis 3 jours."

La signature (-- \nNom | Poste) et les citations répétées (> ...) ajoutent du bruit identique dans tous les emails. Le modèle apprendrait le format au lieu du contenu.

✂️ Caractères spéciaux supprimés, accents FR conservés XLM-RoBERTa est entraîné avec les accents
SUPPRIMÉ : ####### === URGENT === ####### → URGENT SUPPRIMÉ : @@@mention &&& {json: true} → mention # Accents conservés — ils portent du sens ! GARDÉ : "réunion urgente" ≠ "reunion urgente" GARDÉ : "problème critique" ≠ "probleme critique"

Supprimer les accents (é → e) dégraderait les performances en français. XLM-RoBERTa a été pré-entraîné sur des textes avec accents — son vocabulaire en dépend.

✂️ Normalisation des espaces Nettoyage final après suppression des éléments précédents
AVANT : "Le projet est\t\t\tbloqué.\n\n\n\n Merci." APRÈS : "Le projet est bloqué. Merci."

Après suppression des URLs, signatures etc., il reste des espaces multiples, tabulations et sauts de ligne. On ramène tout à un espace simple.

2

Filtrage qualité

Après nettoyage, certains textes sont trop courts pour être analysés, trop longs pour le modèle, ou en double. Ces filtres garantissent la qualité et l'utilité de chaque sample.
📏 Longueur minimale : 5 mots Un texte trop court n'est pas analysable
❌ "OK ✓" → supprimé (1 mot) ❌ "Merci." → supprimé (1 mot) ❌ "Réunion annulée." → supprimé (2 mots) ✅ "Réunion annulée demain matin équipe finance" → gardé (6 mots)

Un texte de 1–4 mots ne donne pas assez de contexte au modèle. "Merci." peut être POSITIVE ou NEUTRAL selon le contexte — sans contexte, c'est du bruit.

📏 Longueur maximale : 300 mots — troncature, PAS suppression Respecter la limite de 512 tokens de XLM-RoBERTa
# Email de 800 mots : Décision : Garder les 300 premiers mots ← tronquer Ne PAS supprimer ← on perdrait des données précieuses # Pourquoi les 300 premiers ? # Le sentiment est presque toujours dans l'objet/introduction du message
💡 XLM-RoBERTa a une limite absolue de 512 tokens (~380 mots anglais, ~300 mots français). Au-delà, le texte est tronqué automatiquement par le tokenizer. On le fait en amont de façon contrôlée plutôt que de laisser le tokenizer couper aléatoirement.
🔍 Déduplication — comparaison sur les 150 premiers caractères Éviter l'overfitting sur des templates répétés
Message A : "Le projet Phoenix est bloqué depuis 3 jours, l'équipe attend..." Message B : "Le projet Phoenix est bloqué depuis 3 jours, l'équipe attend une réponse de la direction" # Les 150 premiers chars sont identiques → B supprimé Cas réel : Templates Jira auto-générés, relances email identiques, notifications Slack répétées toutes les heures

Si le modèle voit 50 fois le même template Jira avec le label BLOCKED, il mémorise le template plutôt que le sens — c'est de l'overfitting. La déduplication l'empêche.

4

Formule de Class Weighting

C'est la technique la plus élégante pour gérer le déséquilibre. Au lieu de modifier le dataset, on modifie la fonction de perte (loss) pendant l'entraînement : les erreurs sur les classes rares coûtent plus cher.

La formule

weight[i] = total_samples / (num_classes × count[i])
weight[i] = poids de la classe i total_samples = nb total d'exemples num_classes = nombre de classes count[i] = nb d'exemples de la classe i

Application numérique — avec le dataset de référence

Classe count[i] Calcul Poids Interprétation
POSITIVE 1 200 2 400 / (3 × 1 200) 0.67 Classe majoritaire → poids faible
NEUTRAL 800 2 400 / (3 × 800) 1.00 Classe médiane → poids neutre
NEGATIVE 400 2 400 / (3 × 400) 2.00 Classe minoritaire → poids élevé

Ce que ça change concrètement pendant l'entraînement

# SANS poids → CrossEntropyLoss standard # Toutes les erreurs sont traitées pareil : Se tromper sur un POSITIVE → pénalité = 1.0 Se tromper sur un NEUTRAL → pénalité = 1.0 Se tromper sur un NEGATIVE → pénalité = 1.0 ← injuste ! NEGATIVE est rare # Le modèle peut "tricher" : prédire toujours POSITIVE # → 50% accuracy sans rien apprendre # AVEC poids → CrossEntropyLoss(weight=[0.67, 1.0, 2.0]) Se tromper sur un POSITIVE → pénalité = 0.67 ← moins grave, c'est fréquent Se tromper sur un NEUTRAL → pénalité = 1.00 Se tromper sur un NEGATIVE → pénalité = 2.00 ← grave ! C'est rare et précieux # Le modèle fait maintenant des efforts sur les classes rares

Implémentation dans WeightedTrainer

# ml/finetune.py — WeightedTrainer import torch from transformers import Trainer from torch.nn import CrossEntropyLoss class WeightedTrainer(Trainer): def compute_loss(self, model, inputs, return_outputs=False, **kwargs): labels = inputs.pop("labels") outputs = model(**inputs) logits = outputs.logits # Poids calculés à partir du dataset d'entraînement class_weights = torch.tensor([0.67, 1.00, 2.00], device=logits.device) loss_fn = CrossEntropyLoss(weight=class_weights) loss = loss_fn(logits, labels) return (loss, outputs) if return_outputs else loss
✅
Intuition : imagine que tu es prof et que tu notes un examen. Si 10 élèves ont réussi la question 1 et seulement 2 ont réussi la question 5, tu vas valoriser davantage les erreurs sur la question 5 pour comprendre ce qui bloque. C'est exactement ce que font les class weights avec le modèle.

Propriété mathématique de la formule

La formule garantit que si toutes les classes étaient équilibrées (count[i] = total / num_classes), tous les poids seraient égaux à 1.0 :

# Si POSITIVE = NEUTRAL = NEGATIVE = 800 (équilibré) weight[POSITIVE] = 2400 / (3 × 800) = 2400 / 2400 = 1.0 weight[NEUTRAL] = 2400 / (3 × 800) = 1.0 weight[NEGATIVE] = 2400 / (3 × 800) = 1.0 # → Dataset équilibré = loss standard, aucune correction nécessaire

Plus la classe est rare, plus son poids est grand. Plus elle est fréquente, plus son poids s'approche de 0. La formule est auto-adaptative au déséquilibre de n'importe quel dataset.
